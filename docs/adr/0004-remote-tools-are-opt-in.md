# ADR-0004 · 跨端工具调用必须显式白名单

状态：已采纳（2026-11-09，v0.2）

## 背景

v0.1 的跨端能力只有"给对方的 agent 发消息"和"传文件"。v0.2 要加 `peer_tool`：
在对方机器上**执行一个具名工具**，拿回结果。这比消息危险得多——它绕过对方的模型判断，
直接调用对方的能力（可能包括读文件、跑命令）。

## 决策

1. 接收方用 `exposedTools` **显式点名**哪些工具可被跨端调用，**默认空**。
   空列表不是"没配置"，是"一个都不给"。
2. 名单外的名字一律 `403 tool-not-exposed`，并记 `denied` 审计——包括试探。
3. 每次调用都走同一条审核闸：`confirm` 模式要人点头；`open` 模式直通（放行时已确认过）。
4. 调用在接收方的**跨端会话**里、以接收方 agent 的身份执行，台账上看得见。
5. 调用方先用 `peer_tools` 拿到真实名单，**不允许猜名字**。

## 理由

- "装上插件 = 把本机能力簿打开"是不可接受的默认值。默认关闭，然后由人一次一个点名，
  这个默认值才配得上"跨端"两个字。
- 只给消息是安全的，但表达能力太弱：对方 agent 可能没有合适的工具，或者模型选择不稳定。
  具名调用让"确定性的能力"也能跨端用。
- 探测试错本身是攻击行为，所以要留下痕迹（`denied` 审计），而不是静默 404。

## 后果

- 想用 `peer_tool` 的人必须先改配置；面板上不提供"一键开放全部"。
- 白名单是"工具名"，不区分参数：一个开放了的 `read_file` 就意味着对方能读本机任意路径。
  所以开放前要看清楚这个工具读的是哪棵目录——这是使用者的责任，写进了 README 的警示。
- 工具名在两端可能重名不同义（对方的 `search` 不一定是你的 `search`）；这是"跨端"的固有成本，
  不做名字映射。
