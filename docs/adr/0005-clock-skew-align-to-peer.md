# ADR-0005 · 时钟偏差靠"对齐对端的钟"解决，不放宽时间窗

状态：已采纳（2026-11-10，v0.2.2）

## 背景

签名请求带 `x-ca-ts`，接收方按 ±60 秒窗口判它新不新（`CLOCK_SKEW_MS`，同时是 nonce 缓存 TTL 的一半）。
这个窗口是防重放的一部分：时间戳离现在太远的请求，即使签名对也不该生效。

真机联调时撞上一个很常见的现实：一台机器的墙钟比另一台快 **118 秒**（Windows 上没权限校时、
或自动校时被域策略/虚拟机快照关掉了）。结果不是"偶发失败"，而是这台机器发来的**每一个**请求都
`401 clock-skew`，两边插件都健康却完全不通。

## 决策

1. **不放宽窗口**：`CLOCK_SKEW_MS` 仍是 60 秒。放宽到 5 分钟只是把同一类故障推迟到下一次偏差更大时。
2. **把窗口平移到对端自己的钟**：接收方按对端广播的 `ts`（发现层 beacon，同一个墙钟）和它
   HTTP 响应里的 `Date` 头估一个偏差 `offset`，接受条件变成
   `|now - ts| ≤ 60s` **或** `|(now + offset) - ts| ≤ 60s`（`src/clock.js`）。
3. **发送侧用同一个偏差签名**：`x-ca-ts = now + offset`。第一次收到 `401 clock-skew` 时，
   从响应 `Date` 头学一次偏差，**只重试一次**。
4. 偏差超过 **1 小时**的不采信，并且清掉旧值：那已经不是"没校时"，是坏掉了。

## 理由

- 平移不改变窗口宽度：任意一条请求仍然只在 ±60 秒内可能被接受，nonce 缓存覆盖 2 × 60 秒，
  所以防重放强度与原来相同。放宽窗口则会实打实地扩大重放面。
- 偏差的观测值全是**未经认证**的信道（广播 beacon、`Date` 头）。这没关系：要利用它绕过认证，
  仍然需要那个对端的共享密钥（HMAC 照验）。伪造成本落到的顶多是"让某个对端的请求验不过"。
- 一台没校时的机器不会自己变好。所以偏差要被**看见**：接收侧每 10 分钟最多记一条
  `[dsh-cross-agent] 对端 … 的时钟与本机相差约 N 秒` 警告。

## 后果

- 两端**不必同时升级**：接收侧容忍、发送侧对齐，任一方向都能单独生效。
  （本次就是只升级了 macOS 一侧，Windows 侧仍是 v0.2.1。）
- 偏差估计来自 beacon，所以发现层被防火墙挡住时，第一次请求会先失败一次再靠 `Date` 头自愈。
- 不解决的问题：偏差到小时级的机器仍然不通——那是真坏了，应该去校时。
