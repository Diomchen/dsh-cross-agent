# ADR-0006 · 远端可以在本机建会话，但权限上限由本机定

状态：已采纳（2026-11-10，v0.2.4）

## 背景

有人问：能不能在 A 机器上让 B 机器新建一条会话，并且指定（或新建）它的项目分组？
宿主的三个能力让这件事成立：

- `workspaceController.create({ path })`：用目录注册项目分组，**幂等**——已有目录复用；
- `sessionController.create({ workspaceId })`：新建会话并挂进分组；
- `permissionPresets.set(session, preset)`：给这条会话定权限档。

但"远端能在我机器上开会话"比"远端能给我发消息"重得多：新会话会花我的额度、能进任何项目、
还能按它的意愿选权限。默认把它做成一键能力，等于把账号的一部分交出去。

## 决策

1. **默认开**：`allowRemoteSessions` 默认 `true`——但每一次都走现有审核闸
   （`confirm` 模式要人点头；`open` 模式直接执行），并记 `session` 审计。
2. **权限由接收方封顶**：配置 `sessionPermissionRules: [{path, preset}]`（最长前缀匹配）
   加 `sessionPermissionDefault`。远端请求里的 `permission` 只能**往紧里调**；
   比上限更松的一律夹到上限，并在结果里回 `clamped: true` 与 `requestedPermission`。
3. **要放开提权得显式改配置**：`allowRemotePermissionRaise: true`。这一条不给默认值。
4. **目录决定分组**：`path` 必须是对方机器上已存在的绝对目录；已经注册过的目录复用原分组，
   没注册过的当场注册。这样"项目分组"不是另一个需要同步的实体，它就是目录本身。

## 理由

- 权限是这件事里唯一真正危险的部分。把"请求"和"上限"分开，远端就无法靠改参数把自己放开——
  它只能选择"更安全"，这符合跨端默认收紧的方向（ADR-0004 同一套思路）。
- 目录即分组：宿主的 workspace 本身就是"一个目录 + 标题"。让远端传 workspaceId 反而要求两边
  同步一份 id 表；传目录路径则天然幂等，且人能一眼看懂。
- 不做"远端删会话 / 改分组"：能建就够了，删除是不可逆动作，留给本机的人。

## 后果

- 远端建出来的会话，标题默认是目录名，可传 `title` 覆盖（截断到 120 字符、去控制字符）。
- 权限没设上（宿主没 `permissionPresets`）时只记一条告警，不让整条请求失败——会话建出来了，
  权限退回宿主默认值。
- 新建的会话不会自动成为"跨端会话"：`peer_ask` 仍然投到固定的那条 `跨端 · <对端>`。
  要让指令落到新会话，需要在协议里再加"投到哪条会话"的参数（未做）。
